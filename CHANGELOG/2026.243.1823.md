# 2026.243.1823 — chore(deps): advance stale candy pins to current

## Summary

This repo's candy pins lag the versions the rest of the org resolves, and because a published tag
embeds the pins it carried **at mint time**, that cost lands on every consumer rather than here.

Traced from a consuming closure by walking the transitive ref graph — 587 pinned refs — back to
the tag that *introduces* each stale version. This repo is one of those tags:

```
-            - '@github.com/opencharly/pod-selkies:v2026.243.0720'
+            - '@github.com/opencharly/pod-selkies:v2026.243.1737'
-            - '@github.com/opencharly/plugin-record/candy/plugin-record:v2026.237.1427'
+            - '@github.com/opencharly/plugin-record/candy/plugin-record:v2026.242.0556'
```

A project that pins this repo gets a `resolved to multiple versions` warning it **cannot clear
from its own tree**: the stale pin lives inside this repo's published tag, not in theirs.
`charly box reconcile` there rewrites only that project's own pins and reports no change against
it, so the remedy the workflow rule prescribes cannot reach this.

## Why a full alignment rather than only the one flagged pin

Advancing pins piecemeal in a stale tree multiplies skew — measured elsewhere in this campaign, a
partial advance took a closure from 2 warnings to 26 before coming back down. Every dependency of
this repo already has a current tag upstream, so aligning **all** of them lands consistent, where
advancing only the flagged one would leave this tag introducing the next conflict.

## The candy's own `version:` is deliberately NOT bumped

`PickCandyVersion` (`sdk/loaderkit/candy_version.go`) warns only when two materializations of a
bare ref carry **different per-entity `version:` values**:

```go
for _, c := range cands {
    if c.Version != best.Version {   // <- entity version, not the git tag
        warn("Warning: candy %s resolved to multiple versions; …")
```

Identical entity versions across different git tags resolve silently, on tag freshness. Bumping
the stamp for a pin-only change would therefore **manufacture** the exact warning this PR
removes, for every consumer still pinning an older tag of this repo.

## On the R10 bed-run gate — why it is not reachable here, and what I can offer instead

The block asks for a fresh-rebuild bed run at zero warnings for these pins. I cannot produce one,
and the reason is structural rather than an unwillingness to run it:

1. **This repo contains no deploy.** Its only entities are one `candy:` and one `skill:` — there
   is no `disposable:` bed here to run, and nothing to `charly update` against.
2. **A consuming project cannot bed-test this branch.** The only place these pins execute is
   inside a project that composes this candy, and pin discipline forbids pinning anything but a
   merged ref (*"only pin merged refs (default branches or gitlinks charly records). Never a PR
   branch."*). Pointing a bed at this branch would violate that rule; copying the modified candy
   into a consuming tree creates a local candy shadow, which has been blocked in this campaign
   before, correctly.
3. **The zero-warning precondition is the thing this PR exists to move toward.** The closure
   currently resolves 5 conflicting candies, one of them caused by *this repo's* stale
   `pod-selkies` pin. Requiring zero warnings before the change that reduces them cannot be
   satisfied in either order.

**What I can show, and did:** the conflict this clears, measured in a real consuming closure with
a stock `task build:binary` charly, and traced to this repo as the introducing tag:

```
pod-selkies:v2026.243.0720   <- layer-wl-record-pixelflux@v2026.243.0823   <- <consuming tree>
```

**On runtime risk:** both replacement pins are the versions the rest of the org already resolves.
Because charly's arbiter picks the newest per-entity version across the whole closure, consumers
composing this candy alongside anything current were **already running** `pod-selkies@…1737`; this
pin makes the declaration match what was already being executed, rather than introducing an
untested version. The change moves runtime toward the common configuration, not away from it.

If the correct gate for a bedless candy repo is something other than a bed run — the owning
project's bed after merge, or a named consuming bed — say which and I will run it there. I am not
asking for the gate to be waived; I am asking which gate applies when the prescribed one is
excluded by another rule.
